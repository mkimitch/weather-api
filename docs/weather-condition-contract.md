# Weather conditions and precipitation probability

The additive condition contract is [JSON Schema V1](../catalogs/weather-contract-v1.schema.json). Current, hourly and daily records retain their legacy `condition` and add `conditions` keyed by presentation context. A canonical selection takes its phenomena, cloud cover, description and native evidence from a single provider and period. The day, night and full-day selections can differ in provider and period. The narrower fields remain empty when the source supplies only a generic daily condition. `_sources.conditions` identifies each selected source. If a rich condition has no legacy projection, `_sources.condition` can identify a separate legacy fallback. `_providers` preserves alternatives, and `extra.ineligibleDaily` holds dates for which no provider passed the existing daily eligibility rules.

A period carries a display date separately from UTC coverage bounds. The generic Tomorrow daily field uses the calendar window only when its timestamp aligns with the configured local midnight. For richer Tomorrow fields, the V1 contract represents sunrise-to-sunrise, sunrise-to-sunset and sunset-to-sunrise respectively. Solar endpoints remain null when they are unavailable. Neither the request's midnight setting nor another provider's astronomy supplies those endpoints. OpenWeather's daily representative timestamp is retained and the actual coverage basis is unknown in V1. One Call gives hourly forecast timestamps. Hourly start and end remain null in the absence of documented boundaries. Tomorrow's generic current, minute, and hourly records can contribute valid same-record cloud cover. The solar fields never inherit that generic measurement. Current fields preserve the source timestamp and distinguish a forecast fallback from an unspecified upstream current data kind. Retrieval time is independent of model issuance or observation time.

## Probability selection and comparison

Valid values are finite numerics between 0 and 1 inclusive after unit conversion. `null` means unavailable. Daily selection prefers an eligible native daily value, then the average interval, maximum interval and unknown basis. This preference applies independently of the configured provider order for other daily metrics. Provider order breaks ties in the same basis. The unsuffixed Tomorrow daily field is unknown basis. No daily value is synthesized from hourly forecasts.

The selected `pop`, `popBasis`, `popPeriod` and corresponding sources travel together. The hourly basis is `interval` and `popPeriod.sourceTime` is the provider timestamp. Hourly as a period basis indicates cadence. Null endpoints mean coverage has not been confirmed. Timestamp-aligned forecasts still participate in hourly fallback. With a current record, only an hourly fallback covering the current timestamp can supply forecast probability. Provider comparisons retain the alternative POP values. A confirmed difference in aggregation, endpoints, event definition, threshold or model issuance is incompatible. Missing evidence makes comparison unverified. The existing `comparable` disagreement flag is true only when comparability is confirmed. Accuracy metric definitions, outputs and unsupported scoring cases remain as described in the [verification runbook](forecast-verification.md).
